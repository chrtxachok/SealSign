# Как ставить задачи ИИ-агенту

Дайте агенту доступ к репозиторию и следующий текст. Он задаёт конечную цель, порядок выполнения, ограничения и обязательные доказательства. Не нужно по одному вручную пересказывать все документы.

## Основное задание — скопировать целиком

```text
Реализуй SealSign до рабочего локального продукта по документации этого репозитория.
Это задача на разработку и проверку, а не на написание ещё одного плана.

Перед изменениями:
1. Прочитай AGENTS.md, README.md, docs/00-source.md и docs/08-decisions.md.
2. Прочитай docs/11-product-development-plan.md, затем документы, относящиеся
   к текущему этапу. Используй docs/10-two-week-execution.md как календарный план.
3. Проверь фактическое дерево, git status и журнал templates/implementation-status.md.
   Не перезаписывай чужие изменения и не повторяй выполненные этапы.

Цель: воспроизводимые data/train/evaluate pipelines, обученный detector двух классов,
общий inference core, CLI, FastAPI, локальное Streamlit-демо, CPU Docker,
измеренные метрики, проверенный README и материалы отчёта.
YAT-19 исключён пользователем. Внешний набор подбери и проверь по docs/09.
Sig & Stamps — кандидат, а не уже проверенный набор. Основная GPU — RTX 4070
пользователя, Colab — резерв. Дедлайн учебной версии — 19.11.2026.

Выполняй S01–S10 из docs/11 последовательно по зависимостям.
Начинай с первого незавершённого этапа. Для каждого этапа:
- проверь входы и критерии перехода;
- реализуй конкретные файлы и поведение;
- выполни подходящие проверки и запиши реальные команды/результаты;
- обнови журнал исполнения: статус, evidence, ограничения и следующий шаг;
- продолжай следующий доступный этап, не останавливайся на очередном плане.
Если зависимость блокирует этап, зафиксируй её и продолжи независимые задачи.
Не помечай этап done без доказательств его критериев.

Обязательные ограничения:
- class_id 0=stamp, 1=signature; единый core для CLI/API/UI;
- оба класса проверены на каждой supervised странице; partial labels не считать фоном;
- split по документным группам до augmentations/tiles, выбор модели и порогов только по val;
- test не использовать для настройки; не выдумывать результаты, лицензии, число страниц;
- не коммитить данные, веса, секреты, .env и приватные изображения;
- не подменять реальные предсказания заглушками; fixtures допускаются только в тестах;
- README содержит проверенные команды, bundle и зависимости имеют фиксированные версии/hashes;
- не запускать платные ресурсы и не публиковать сервис/данные без соответствующего разрешения;
- S11–S12 не входят в текущий запуск: сохранить расширяемость, но не задерживать сдачу.

Если требуется доступ к GPU, файлам, аккаунту или человеческое решение по разметке,
задай конкретный вопрос с указанием блокируемого шага. Не проси пароли/токены в чат.
Не запрашивай повторно YAT-19 или первый отчёт. Пока ждёшь — делай независимую работу.
Не заявляй, что запуск на облачном CPU подтверждает работу на RTX 4070.

В конце сообщи: выполненные этапы, что реально запускается, выполненные проверки,
полученные метрики (только если измерены), текущие блокеры и точный следующий шаг.
Git-действия выполняй в пределах отдельного поручения пользователя; не считай
описание процесса автоматическим разрешением на merge, push или публичный deploy.
```

Этот prompt не гарантирует качество сам по себе: его обеспечивают проверяемые критерии этапов, реальные входные данные и evidence в журнале. Если у агента нет доступа к GPU/данным или некому принять разметку, он должен прямо описать блокер, а не симулировать выполнение.

## Если удобнее выдавать работу по этапам

Используйте шаблон, заменив поля в квадратных скобках:

```text
Выполни этап [Sxx] из docs/11-product-development-plan.md.
Прочитай AGENTS.md и профильные документы. Входные артефакты: [пути/версии].
Предыдущие этапы подтверждены: [evidence/commits].
Реализуй шаги этапа, выполни его проверки и обнови templates/implementation-status.md.
Не расширяй задачу на последующие этапы, кроме необходимых исправлений зависимости.
Если вход отсутствует — укажи конкретный блокер; не создавай фиктивные данные/результаты.
В ответе дай изменения, команды и результаты проверок, статус критериев и handoff.
Git: [например: сделай локальный коммит; push/merge пока не выполняй].
```

Для первого запуска можно выдать S01 и исследование S02: каркас не требует завершённого выбора корпуса. Для S05 необходимы реальные QC/split и доступ к обучению; для S06–S10 — проверенный bundle. Один лишь набор пустых директорий не закрывает S01, а notebook без исполненного обучения не закрывает S05.

## Продолжение в новом чате

```text
Продолжи реализацию SealSign с первого незавершённого этапа docs/11.
Прочитай AGENTS.md, docs/08 и templates/implementation-status.md,
проверь evidence и состояние кода. Сохрани ранее принятые решения,
не повторяй закрытые этапы. Выполни доступные шаги и обнови журнал.
Укажи, какие прежние доказательства удалось проверить и что осталось заблокировано.
```

## Что проверять в ответе агента

- Есть конкретное работающее поведение, а не только список новых файлов.
- Команды действительно исполнены; указана среда и реальные результаты проверок.
- Зафиксированы версии данных, split, config, кода и весов там, где они нужны.
- Слова «готово», «обучено», «протестировано» подтверждены артефактами.
- Есть явная граница между пройденным тестом на fixture и полноценным сквозным запуском.
- Ошибки, недостающие доступы и невыполненные требования перечислены без скрытой подмены задачи.

Если агент пишет «всё готово», а основной сценарий не запускался на настоящей модели, верните ему критерии S06–S10 и попросите evidence. Не нужно требовать переобучение при каждой правке UI: повторять только проверки, на которые влияет изменение.
